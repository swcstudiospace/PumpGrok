# Safety Invariants, Failure Modes, and How Tests Prove Them

Tracker: SPE-18001 https://linear.app/swcstudio/issue/SPE-18001/n7-safety-invariants-failure-modes-and-how-tests-prove-them | Notion https://app.notion.com/p/3ffbc1a0c7ae8170b4ddc3ff4e95cd2c?pvs=204

Node n7 of ultrathink graph ut-mvgfr96y-be17fc96 (steps SPE-18047, SPE-18049, SPE-18051, SPE-18050, SPE-18052, SPE-18053, SPE-18055, SPE-18054). Companion policy document: docs/RISK_POLICY.md (closes node n6 defaults, SPE-18000).

This document is a design only. It enumerates every non-negotiable invariant of the pumpgrok desk, assigns each one exactly one owning test (so a gap is visible as a missing row, never as a shared assertion), lists the failure modes the desk must survive, specifies the fault-injection harness those tests need, and places every test in the implementation phase where it lands. Every repository fact cites `file:line` of the current tree (branch `feat/grokbot-desk-merge`); inferences are tagged `[INFERENCE]`. Names of modules, events, config keys, rule ids and approval kinds follow the orchestrator resolutions R1-R40 (R16-R40 override docs/design/paper-engine.md, docs/design/interfaces.md, docs/TOOL_CATALOG.md, docs/ROSTER.md, docs/MIGRATION_MAP.md and docs/FOUNDATION_STACK.md where they conflict); where a name is introduced here it is marked `(new)`.

## 3. Runtime invariants (class `runtime`)

## 5. Fault-injection harness

Location: `tests/fault_injection.py` (this assignment's placement; the ultrathink spec n7 names `tests/harness/faults.py`). `FixtureClock` lives in `src/pumpgrok/replay/clock.py` (R31) because production replay needs it, so only the fault wrappers are test code. Per R37 the harness lands in Phase 5 Hardening together with the degradation and soak suites; the spec's preference for building it in Foundation is superseded (section 8 item 3).

### 5.1 Design

```python
# tests/fault_injection.py (design listing; not code in this wave)
from dataclasses import dataclass, field
from typing import Literal

FaultMode = Literal[
    "stale",        # return the last good value with an old source_ts; never fresh
    "timeout",      # await clock.sleep(timeout_s + 1) then raise httpx.ReadTimeout
    "stall",        # await an Event that the schedule releases later (exercises cycle_timeout_s)
    "rate_limit",   # raise httpx.HTTPStatusError(429) with Retry-After
    "raise",        # raise the configured exception (default RuntimeError)
    "unwritable",   # LedgerStore.append raises LedgerUnavailable (sqlite3.OperationalError wrapped)
    "malformed",    # return a payload from tests/fixtures/http/adversarial/<name>.json
    "duplicate",    # yield the previous frame again (WS only)
    "slow",         # add latency_s on the clock before answering
    "unknown",      # ExecutionAdapter.place: raise UnknownResult after the ledger OrderPlaced
]

@dataclass
class FaultRule:
    mode: FaultMode
    after_n_calls: int = 0          # start after this many successful calls
    for_calls: int | None = None    # how many calls the fault lasts (None = until cleared)
    at_virtual_time: float | None = None   # alternative trigger on FixtureClock.now()
    for_seconds: float | None = None
    match: str | None = None        # method name or endpoint substring, e.g. "curve", "/coins/", "getAccountInfo"
    payload: str | None = None      # fixture name for malformed
    exc: type[BaseException] = RuntimeError

@dataclass
class FaultSchedule:
    rules: list[FaultRule] = field(default_factory=list)
    calls: dict[str, int] = field(default_factory=dict)      # per method call count
    log: list[tuple[float, str, str]] = field(default_factory=list)   # (virtual_ts, method, outcome)
    def active(self, clock, method: str) -> FaultRule | None: ...
    def clear(self) -> None: ...

class Faulty:
    """Mixin: wraps an inner object; every public coroutine consults the schedule first."""
    def __init__(self, inner, schedule: FaultSchedule, clock): ...

class FaultyDataSource(Faulty):   ...   # wraps DataSource (PumpPortal WS + pump.fun REST): subscribe(), coins(), trades(), holders()
class FaultyPriceSource(Faulty):  ...   # wraps PriceSource: curve(), spot()
class FaultyRpcClient(Faulty):    ...   # wraps tools/onchain/rpc.py client per endpoint index: call(method, params)
class FaultyLLMClient(Faulty):    ...   # wraps core/llm.py client: complete(payload) -> text
class FaultyLedgerStore(Faulty):  ...   # wraps ledger/store.py LedgerStore: append(), snapshot(), read_tail()
class FaultyExecutionAdapter(Faulty):   # wraps PaperAdapter: place() for mode "unknown" only

# pytest fixtures (tests/conftest.py imports them)
#   faults            -> FaultSchedule bound to the test's FixtureClock
#   desk_with_faults  -> builds the desk from contracts/tool-rosters with every source wrapped
#   assert_no_new_buys(ledger, since_ts), assert_escalation(ledger, kind, count=1),
#   assert_breaker(ledger, name, state), advance(clock, seconds, run_supervisor=True)
```

Rules:

- The wrappers are the only way tests inject faults. No test monkeypatches a production module attribute; the supervisor is constructed with the faulty instances through the same constructor arguments production uses (`Supervisor(sources=..., price=..., rpc=..., llm=..., ledger=..., adapter=..., clock=..., rng=...)`), so a fault test exercises the production wiring.
- Faults are deterministic: triggers are call counts or virtual time, never wall time or randomness, so a degradation test is replayable like everything else.
- `FaultSchedule.log` is an assertion surface: tests assert the *order* of outcomes (for example `retry, retry, failover(1), ok`) rather than only the end state.
- `stall` is distinct from `timeout`: `timeout` proves the client timeout path, `stall` proves the supervisor's `cycle_timeout_s` path (a cycle that never returns counts as a crash, docs/design/paper-engine.md:636).
- `unknown` on the adapter is how INV-R-12 is proven: the ledger holds `OrderPlaced` with its consumed `ApprovalRecorded`, the adapter raises after it, and the test asserts the desk reports `status=unknown` and demands fresh approval rather than retrying.
- The harness never imports `vendor/`; characterization tests that need the vendor oracle import it directly from the vendor path and are deleted with the vendor tree.

## 7. What is hardest to prove, and the order of work

1. Live-write isolation (INV-S-01, INV-S-03, INV-C-03). Hard because the negative must hold over the whole tree including future code; the AST test must be strict enough to catch `getattr(client, "send" + "Transaction")` style evasion yet not fail on the words in docs or error messages. Mitigation: the quarantine is one package (`execution/live/`, R31), the forbidden list is a module-level constant shared with the G-7 port, and the test prints the offending `file:line:col` so false positives are fixable in minutes.
2. Soak (INV-R-36). Hard because memory growth is noisy under CPython; the test measures growth *after* the first virtual hour, samples `tracemalloc` top allocations on failure so the leak is attributable, and runs nightly on `soak-3d` with a 10-minute `smoke-10m` twin on PRs so a regression is caught within one wave.
3. Multi-fault degradation (INV-R-32 .. INV-R-35). Hard because several breakers and the supervisor interact; solved by the harness's deterministic schedule and `FaultSchedule.log` ordering assertions, and by running every degradation test on `FixtureClock` so a 300 s blind window costs milliseconds. R37 defers the harness to Phase 5, so Phases 2-4 prove their own behaviour with `respx`, fixture holes (the 180 s gap in `smoke-10m`) and direct store manipulation, and the degradation suite re-proves them under injected faults.
4. Kill switch within one cycle and at `CONFIRMING` (INV-R-01). Timing-sensitive only on a wall clock; on `FixtureClock` the assertion is exact (set at `t`, advance 5 s, assert no buy with `ts > t`; park an order in `ACCEPTED`, flip the file, assert `OrderRejected`).
5. Single writer across processes (INV-R-21, INV-R-35). `BEGIN IMMEDIATE` makes it correct; the test must interleave a CLI append with the supervisor's without wall-clock races, which the `FixtureClock` and an explicit barrier in the harness provide.

Order: static and config tests in Phase 1 (they pass trivially on the skeleton and then guard every later batch); quarantine, characterization and `respx` failover in Phase 2; absence, manifest and input-validation tests in Phase 3; the risk/ledger/supervisor/replay suite in Phase 4; harness, degradation, soak and the matrix meta-test in Phase 5.
